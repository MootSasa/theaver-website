Чтобы клиент не скачивал всю переписку заново после сна или переключения сети, сервер ведёт монотонный журнал событий пользователя (**`usn` — Update Sequence Number**), дополняя его идемпотентностью исходящих сообщений и указателями High-Water Mark.

## Инкрементальные обновления через `since_usn`

<ApiEndpoint method="GET" path="/api/updates?since_usn=0&limit=200" auth="JWT" />

Параметры запроса:

| Параметр | Тип | Диапазон / По умолчанию | Описание |
|---|---|---|---|
| `since_usn` | `int64` | `>= 0` (по умолчанию `0`) | Последний `usn`, надёжно сохранённый в локальной БД |
| `limit` | `int` | `1..500` (по умолчанию `200`) | Максимум событий на одну страницу ответа |

Формат ответа:

```json
{
  "success": true,
  "too_long": false,
  "events": [
    {
      "usn": 48219,
      "event_type": "new_message",
      "chat_id": 849201432,
      "payload": { "...": "..." },
      "created_at": "2026-11-28T10:14:22Z"
    }
  ],
  "max_usn": 48219,
  "has_more": false
}
```

### Работа с `has_more` и `too_long: true`

- Запрашивайте `GET /api/updates?since_usn=<max_usn>` в цикле, пока `has_more === true`, сохраняя `max_usn` в одной транзакции с применёнными изменениями.
- События хранятся в журнале **14 дней**. Если клиент был офлайн дольше срока хранения или передал устаревший курсор, сервер вернёт `too_long: true`.
- Получив `too_long: true`, сбросьте локальный курсор, перечитайте список диалогов через `GET /api/chats`, обновите открытые чаты через `GET /api/chats/:id/messages` и зафиксируйте новый `max_usn`.

## Идемпотентная очередь отправки (`local_id`)

Перед отправкой сохраняйте сообщение локально со сгенерированным уникальным токеном `local_id` (`client_message_id` принимается как синоним) и передавайте его в REST `POST /api/chats/:id/messages` или WebSocket RPC `send_message`.

- На таблице сообщений в PostgreSQL действует уникальное ограничение `UNIQUE (chat_id, sender_id, client_message_id)`.
- Если связь оборвалась после сохранения на сервере, повторная отправка с тем же `local_id` вернёт `{ "ok": true, "deduplicated": true, "message": { ... } }` без создания дубликата.

## Указатели прочтения High-Water Mark

Вместо флагов на каждом сообщении сервер хранит два монотонных ID-указателя на участника чата:

- `last_read_inbox_message_id` — максимальный ID входящего сообщения, прочитанного текущим пользователем (управляет бейджем непрочитанных).
- `last_read_outbox_message_id` — максимальный ID отправленного сообщения, до которого дошёл собеседник (галочки прочтения).

Продвигайте входящий указатель по REST (`POST /api/chats/:id/messages/read` или `POST /api/chats/:id/messages/read-up-to` с `{ max_id }`) или через WebSocket RPC `read_history`. Указатели двигаются только вперёд и автоматически рассылают `message_read` и `unread_count_updated` на остальные ваши устройства.
